# Design directions (T16)

Three directions for the playground, each as a navigable page with **real data**: the diamond program (`tests/fixtures/prueba/1- Ciclos.txt`) run by the rebuilt interpreter. The step, the variables, the output rows, the symbols and the tree on screen are what `run()` returned, not invented. Henry picks one (approval gate b); nothing visual is decided before that.

## How to look at them

Open `docs/design/mockups/proof.html`, `reel.html` or `grove.html` in a browser (they work from the file; the fonts come from Google Fonts, so they need a connection). Each opens at step 4,200 of 13,228. You can step (◂ ▸), play, drag the slider, switch tabs, and narrow the window to 375 px.

What is real and what is staged:

| Real | Staged |
|---|---|
| Source, highlighting (from the real lexer), 13,228 steps, 26 output rows, symbols, the variables at each step, "changed" marks, the syntax trees | The page jumps every 100 steps (134 snapshots), because a static page cannot run the interpreter. The real product replays every step |
| The two problems in the Problems tab are real diagnostics | They come from `basicas.oak` (the diamond has none), and the page says so |
| | Run, Stop and Examples do nothing |

`data.js` is generated by `scripts/mockup-data.ts` (`npx tsx scripts/mockup-data.ts`).

## What every direction has to carry

The same slots, so the choice is about look and emphasis, not features: the source with the executing line marked; the variables with what just changed; the output; Problems, Syntax tree and Symbols; the controls to step, play and scrub; one accent colour; no gradients, no purple, no card soup. At 375 px the views become tabs (spec AC-33).

## A — Proof

*Light. The program as a typeset page, with its values written in the margin.*

- **Idea:** like proofreading. Each line that assigns a variable shows its current value in the right margin (`absolutoi = 8.0`), so you read the program and its state in one glance. The executing line gets a vermilion bar and a red line number, like a correction mark.
- **Look:** paper `#f2eee4`, ink `#14130f`, one vermilion `#c9340e`. Instrument Sans for the interface, Spline Sans Mono for code. Ruled tables, small-caps labels, a thick rule on top; Swiss-print in spirit.
- **Strong:** the most readable; values next to the code is the feature that explains a run fastest; simplest to build (a CodeMirror gutter and a line decoration); the light theme is the one the other portfolio projects do not have (Rung, BugLab are dark).
- **Risk:** the margin column competes with long lines (the diamond's lines 24 and 25 get cut; the real editor would scroll sideways). Less "wow" than B.
- **Phone:** tabs Code / State / Views; the margin values go away (the State tab holds them).

## B — Reel

*Dark. The run as a timeline you can scrub, like a video editor.*

- **Idea:** time first. The bottom third is a timeline with lanes drawn from the real trace: which **line** was running (the diamond's nested loops show as a sawtooth), which **conditions** held, how much was **printed**, and the values of `i` and `j` over the whole run. Drag anywhere on it to move through 13,228 steps.
- **Look:** near-black `#0e1012`, warm white text, one mint-cyan `#4fe3c1` (the playhead and everything "now"). Archivo and Red Hat Mono. Variables as small "watch" cards.
- **Strong:** the most striking, and the one that shows the run as a whole, not one step at a time. Loops and recursion become visible shapes.
- **Risk:** dark and bright accent like Rung and BugLab, so the portfolio looks alike; the timeline is a custom drawing (canvas or SVG, with an accessible slider on top), the most work of the three; the code area is shorter because the timeline takes the bottom.
- **Phone:** tabs Code / Inspect with a compact timeline always visible.

## C — Grove

*Cream and forest green. The syntax tree is the centre.*

- **Idea:** structure first. Three columns: the code, **the tree of the statement being run** (the condition's tree lights up with its result, `false`, on the root), and the state. It is the one that teaches *how an interpreter reads a program*; the name OakLand gets a leaf and a tree.
- **Look:** cream `#f4f0e4`, forest ink `#1b2a1f`, moss green for structure, one sun-orange `#b85e08` for "being evaluated". Fraunces (display, used sparingly), Hanken Grotesk, DM Mono. Squared chips joined by thin lines, not rounded cards.
- **Strong:** the most distinctive concept and the best fit for someone learning compilers; the tree is a view no ordinary debugger has.
- **Risk:** trees get wide (one condition of the diamond already fills the middle column); the tree changes less than the variables as you step, so it is the least "alive" of the three; needs a tree-layout component; heaviest on a phone (horizontal scroll inside the Tree tab).
- **Phone:** tabs Code / Tree / State.

## Recommendation

**A, with B's timeline as its transport.** A is the clearest and cheapest and the only light one; B's line-and-output lanes are the best use of the trace data and replace A's plain slider with something that says more about the run (one SVG, a few hours). C's tree stays where A already puts it: the Syntax tree tab. This is a recommendation, not a decision: B on its own and C on its own are both defensible, and if you want a dark theme B is the one.
